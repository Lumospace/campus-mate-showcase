# 架构说明

本文档描述「校遇」的系统架构、模块划分、数据模型与关键设计取舍。**不包含**服务端具体实现代码。

---

## 一、整体架构

```
浏览器（Vue 3 SPA）
   │  HTTPS
   ▼
Nginx（反向代理 / 静态资源 / 请求体大小限制）
   │
   ├── /            → client/dist 静态文件
   ├── /api/*       → Express 5（REST）
   └── /socket.io/* → Socket.IO（WebSocket）
                        │
                        ▼
                 SQLite（WAL 模式）
```

设计取舍：

- **单体而非微服务**：校园场景用户规模有限，单机 Node 进程 + SQLite 足以支撑，省去分布式事务与运维成本；
- **零原生依赖**：数据库使用 Node 22+ 内置的 `node:sqlite`，部署时无需编译原生模块，服务器上 `npm install` 即可跑起来；
- **同步数据层**：`node:sqlite` 为同步 API，在单进程模型下天然串行，不会出现并发写交错；一旦引入 `await` 或多进程，必须补事务与并发控制（这一点在代码约定中已明确）。

## 二、服务端模块划分

| 模块 | 职责 |
| --- | --- |
| 入口层 | 加载配置与 `.env`、注册路由、挂载静态资源、统一错误处理、启动 Socket 与定时任务 |
| 数据层 | 建表、索引、幂等迁移（用独立标记位记录迁移是否已执行）、事务封装 |
| 认证层 | JWT 签发与校验、密码哈希、邮箱白名单校验、封禁拦截、管理员权限位校验 |
| 路由层 | 按业务域拆分：账号、用户、需求、申请、队伍、邀请、互评、治理、通知、管理后台、故事墙、校园活动、快闪、兴趣圈、成长、反馈、AI |
| 匹配层 | 五维可解释匹配计算与推荐解释文案生成 |
| 信誉层 | 信誉分状态机、档位判定、勋章发放 |
| 过滤层 | DFA 敏感词匹配（内容发布前拦截） |
| 通知层 | 站内通知落库、合并降频、可点击跳转 |
| 实时层 | Socket.IO 鉴权、按队伍房间广播、消息撤回同步 |
| 调度层 | 定时任务：活动开始、封禁到期解封、受限到期解除、通知清理，均带异常隔离 |
| 邮件层 | 腾讯云 SES 签名与验证码邮件发送 |

> 上述模块只做职责说明，实现细节不在公开范围。

## 三、数据模型（按域分组）

共约 40 张表，按业务域划分如下（仅列职责，不含字段定义）：

**账号与身份**
`users`（用户与画像）、`student_verifications`（学号核验）、`user_agreements`（协议版本留痕）

**需求与组队**
`demands`（需求）、`applications`（申请与蹲补）、`standby`（蹲补记录）、
`teams`（队伍）、`team_members`（成员与已读序号）、`team_invites`（邀请）、
`exit_requests` / `disband_requests` / `disband_votes` / `transfer_requests`（队伍变更审批链）

**协作与评价**
`messages`（聊天消息）、`reviews`（搭后互评）、`credit_logs`（信誉分流水）、`badges`（勋章）

**治理与安全**
`reports`（举报）、`appeals`（申诉）、`blocks`（拉黑）、`dislikes`（不感兴趣）、
`admin_actions`（管理员操作留痕）、`notifications`（站内通知）、`favorites`（收藏）

**内容与社区**
`circles` / `circle_members` / `circle_posts` / `circle_post_replies`（兴趣圈）、
`stories` / `story_likes` / `story_comments`（故事墙）、
`campus_activities` / `activity_signups` / `activity_favorites` / `activity_publish_requests`（校园活动）、
`flash_requests` / `flash_members`（快闪组局）

**其他**
`app_meta`（迁移标记位等元信息）、`ai_messages` / `ai_quota` / `ai_story_quota`（AI 限额）、`feedback`（用户反馈）

### 一致性策略

- 多步状态变更统一包裹事务，任一步失败整体回滚；
- 所有时间戳由数据库函数写入本地时区字符串，避免 UTC 偏移导致前端显示错位；
- 迁移使用幂等写法（`CREATE TABLE IF NOT EXISTS` + `PRAGMA table_info` 判断列是否存在），并用 `app_meta` 中的独立标记位记录一次性迁移，防止重启重复执行。

## 四、关键设计

### 1. 匹配可解释性

推荐不能只是「猜你喜欢」。引擎输出分数之外，还必须能回答「为什么是他」。因此每个维度都保留可读的中间量（兴趣交集标签、重合时段、合作次数），最终拼装成人话解释。

### 2. 状态机与联动清理

状态变更最容易出问题的地方不是主流程，而是**联动**：需求下架要清理申请与蹲补、封禁用户要下架其需求并解散其队伍、队伍满员要让其余待处理邀请失效。这些联动统一在事务内完成，且每条都会通知受影响用户，避免出现「点得动但必然失败」的按钮。

### 3. 实时消息与未读

- Socket.IO 以队伍 ID 为房间，进房校验成员身份；
- 每条消息带自增序号，成员表记录已读序号，未读数为 `max(seq) - last_read_seq`；
- 用户正在该聊天室时不弹提醒；同一队伍 30 秒内合并提醒；
- 组件卸载时主动离开房间，避免残留订阅导致错推。

### 4. 安全实践

| 风险 | 措施 |
| --- | --- |
| 密码泄露 | scrypt 加盐哈希，统一 8~20 位含字母与数字的强度校验（前后端双校验） |
| 会话伪造 | HMAC-SHA256 JWT，密钥优先取环境变量，其次落盘文件 |
| 暴力破解 | 登录/注册按 IP 限流，验证码发送单独更严限流 |
| 越权访问 | 路由守卫校验权限位；服务端对每次资源操作二次校验归属 |
| 内容风险 | DFA 敏感词过滤，命中即拦截并提示具体词 |
| 上传体积 | 图片 1MB、附件 5MB、请求体上限 50MB，Nginx 同步配置 |
| 密钥管理 | 第三方密钥只走环境变量，代码中不落明文（生产配置不入库） |
| 数据一致性 | 多步写操作事务包裹，管理员操作全量留痕 |

### 5. 性能实践

除 README 中记录的兴趣圈图片优化案例外，还有几处通用的处理方式：

- 列表接口只返回必要字段，大字段（图片、长文本）走独立接口；
- 高频统计改为聚合子查询或 `GROUP BY` 一次取回，避免 N+1；
- 用户活跃时间更新做 5 分钟节流，减少 WAL 写放大；
- 通知表只保留近 30 天，定时物理清理；
- 定时任务内维护的内存集合定期清理失效项，避免长跑进程内存增长。

## 五、部署形态

```
systemd 托管 Node 进程（127.0.0.1:3000）
Nginx 终止 TLS 并反代，托管前端构建产物
SQLite 单文件数据库 + WAL
```

发布流程为：本地构建前端 → 打包源码与产物 → 传输到服务器 → 备份旧版本 → 覆盖 → 重启服务 → 健康检查。密钥与服务器信息均不进入代码仓库。
