# 校遇 · CampusMate

> 不必独行，在校有遇 —— 一个面向校园场景的「搭子」匹配与组队协作平台。

「校遇」解决的是校园里高频但难撮合的需求：找一个一起自习的人、一顿饭的搭子、一场球、一次比赛的队友。平台以**五维可解释匹配引擎**为核心，把「发布需求 → 智能推荐 → 申请组队 → 队伍协作 → 搭后互评 → 信誉沉淀」串成完整闭环，并用信誉体系与内容治理保证组队过程的安全可信。

本仓库是该项目的**作品展示仓库**，用于呈现工程结构、前端实现与架构设计，**不包含服务端核心业务实现**（详见下方「关于本仓库」）。

## 核心设计

### 1. 五维可解释匹配引擎

推荐分不是黑盒打分，而是五个可解释维度的加权聚合：

```
score = Σ(维度权重 × 维度得分) / Σ参与维度权重
```

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 兴趣重合度 | 0.30 | 双方兴趣标签的 Jaccard 相似度 |
| 空闲时间窗重合 | 0.25 | 按周内时段网格计算可共同出行的时间占比 |
| 发起人信誉 | 0.13 | 信誉分归一化 |
| 老搭子加成 | 0.12 | 历史合作次数带来的信任加成 |
| 对方活跃度 | 0.08 | 近期活跃程度 |

当新用户没有组队史时，「老搭子」维度自动退出，其余维度按权重重新归一化 —— 避免新用户被系统性降权。每条推荐都会生成一句 `hint` 解释「为什么推荐给你」，让匹配结果可被用户理解和质疑。

### 2. 可信组队状态机

需求从 `recruiting` 到 `matched`、队伍从 `forming` 到 `active` 再到 `done/dismissed`，每一次状态流转都有前置校验与联动清理：满员自动锁定、成员退出触发缺员恢复、队伍解散同步清理待处理申请与蹲补记录、活动开始后禁止交易式操作。所有多步变更包裹事务，保证不会出现「超员」「幽灵队伍」这类不一致状态。

### 3. 信誉与治理闭环

搭后互评产生星级与标签，信誉分按规则增减并驱动档位变化（观察 / 友好 / 靠谱 / 金牌）；举报、申诉、封禁、下架构成治理链路，所有管理员操作自动留痕（操作人、时间、缘由），并同步通知到当事人。

### 4. 消息中心与实时通信

通知与聊天统一为单一入口：未读角标合并两类消息，浏览器标签页标题实时显示未读总数；聊天室基于 Socket.IO 房间机制，支持消息撤回、只读历史、进房即销未读。

### 5. 一次真实的性能优化

上线后发现兴趣圈详情页频繁出现 `timeout of 15000ms exceeded`。定位过程与结论：

- 帖子图片以 base64 data URL 内联存储在帖子记录中，单条帖子 `images` 字段达 **4.88 MB**；
- 详情页进入时并发拉取「帖子列表（含大图）+ 圈友列表（含大图头像）」，公网带宽下响应耗时超过 90 秒，必然击穿 15 秒超时；
- 同时存在 N+1 查询：每帖单独查回复数、每位圈友单独查两项统计。

优化方案：

1. 列表/详情接口只返回 `image_count`，图片改走独立的二进制接口，附带 `Cache-Control` 与 `ETag`，二次浏览走缓存；
2. 前端用 `IntersectionObserver` 做视口懒加载，图片以 blob 形式按需请求，点击大图时才加载整组；
3. 圈子成员数、帖子回复数、圈友共同圈数与组队次数全部改为聚合查询，消除 N+1；
4. 上传前用 Canvas 压缩（长边 1280、JPEG 逐步降质，控制在 1MB 内），从源头控制体积。

结果：帖子详情接口从 **4,886,391 字节 / 98.6 秒** 降至 **518 字节 / 0.87 秒**，单张图片独立加载约 610 KB / 1.2 秒，超时问题消失。

## 目录结构

```
campus-mate-showcase/
├── client/                 # 前端完整实现
│   ├── index.html
│   ├── vite.config.js
│   └── src/
│       ├── views/          # 28 个页面（大厅、推荐、发布、我的搭子、聊天、兴趣圈…）
│       ├── components/     # 通用组件（图片查看器、AI 助手、反馈弹窗）
│       ├── composables/    # 组合式逻辑（如图片视口懒加载）
│       ├── layout/         # 应用骨架与顶栏导航
│       ├── store/          # Pinia 状态（登录态）
│       ├── api/            # axios 封装与接口定义
│       ├── router/         # 路由与登录守卫
│       ├── styles/         # 设计变量与全局样式
│       ├── socket.js       # Socket.IO 客户端封装
│       └── utils.js        # 时间格式化、图片压缩等通用工具
├── docs/
│   ├── 功能说明.md          # 逐项功能说明（功能 → 需求 → 界面）
│   ├── 架构说明.md          # 后端模块划分、数据模型、实时通信与安全设计
│   └── API清单.md           # 接口清单（按模块分组）
└── server/                 # 服务端骨架说明（不包含实现）
```

## 关于本仓库

**公开内容**：前端完整源码、产品功能文档、系统架构与数据模型说明、接口清单。

**未公开内容**：服务端业务逻辑与路由实现、匹配算法实现、信誉与风控规则的具体实现、敏感词库、数据库初始化与种子数据、部署密钥与生产环境配置、任何真实用户数据。

这样安排的原因很直接：线上站点本身已在浏览器端分发打包后的前端代码，前端源码的公开不会带来额外风险；而服务端的算法与规则才是这个产品的核心资产，因此仅以架构文档的形式呈现设计思路。
